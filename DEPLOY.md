# Развёртывание

Готовое к бою решение в двух вариантах, оба из одного репозитория, один конфиг
и один процесс:

| режим | где | зачем |
|---|---|---|
| Docker-стенд | Windows (это машина разработки) | подготовка, тренировка, проверка правил |
| Реальный хост | Linux с `systemd` | соревнование |

Код одинаковый. На соревновании меняются **только адреса, пароли и пределы
нагрузки** (см. `MONITORING.md`, разделы «Правка 1..4»).

---

## 1. Docker-стенд (локально, Windows)

```powershell
.\deploy\stand-up.ps1          # build + up + ждёт healthy
.\deploy\stand-verify.ps1      # автоматическая предполётная проверка (без API)
.\deploy\stand-verify.ps1 -Password ops@1234   # + проверка /api/flags и /api/checker
.\deploy\stand-down.ps1        # снять стенд (данные и БД остаются)
.\deploy\stand-down.ps1 -Clean # + удалить тома
```

Что видит оператор: ingress `http://127.0.0.1:9090`, UI `http://127.0.0.1:8787`
(логин `ops`), файлы захвата `services/monitoring/data/`.

`stand-verify.ps1` проверяет живыми запросами: маршрут доходит до сервиса,
подсеть команды рвёт `.git`, чекер и незнакомец проходят, флаги и md5-артефакт
попадают в файлы. Истина берётся из файлов захвата, а не из HTTP-кода, поэтому
ложноположительный «порт упал» не маскирует результат.

## 2. Реальный хост (Linux, соревнование)

### Что нужно собрать у оператора перед приездом

1. **Подсети участников** — по одной на команду (это то, по чему полисуется).
2. **Адреса служб**, которые живут на хосте: `сервис → порт → апстрим`.
3. **Адрес машины оператора** (`admin`), чтобы в UI попадали.
4. **Адрес чекера**, если организация его даёт (необязательно — чекер проходит
   и без записи, просто будет подписан как `unknown`).
5. **Порты, которые слушают сервисы на хосте**, — для режима перехвата портов
   (пункт 2.4), если команды ходят по `IP:порт` без DNS-имён.

### 2.1 Автоматическая установка

На машину с `git`, `node >= 20`, `npm` и правами `root`:

```bash
cp deploy/competition.example.json deploy/competition.template.json
# заполнить адреса и routes
AD_OPS=секрет_оператора \
AD_ALPHA=секрет_команды_alpha \
AD_BETA=секрет_команды_beta \
bash deploy/install-linux.sh
```

Скрипт: собирает с нуля (`npm ci` + `tsc`), ставит в `/opt/ad-gateway`, генерирует
`config/gateway.json` из шаблона (пароли хешируются, открытым текстом не
ложатся нигде), ставит unit `ad-gateway` и стартует его.

### 2.2 Пароли и генерация конфига

Пароли не живут в файлах: в шаблоне у каждого аккаунта поле `password_env`,
скрипт берёт значение из переменной окружения и тут же превращает в scrypt-хеш.
Один аккаунт можно кормить через общий `$AD_PASSWORD`.

Генератор валидирует всё тем же парсером, что и заргужка гейта: конфиг, который
гейт отказался бы принять, не пишется на диск вовсе.

```bash
node packages/gateway/dist/setup.js \
  --template deploy/competition.template.json \
  --out config/gateway.json
```

### 2.3 Запуск как сервиса (systemd)

Unit `deploy/gateway.service`:

- `User=node`, рабочий каталог `/opt/ad-gateway`;
- env: `AD_GATEWAY_CONFIG`, `AD_DATA_DIR` (туда пишутся JSONL), лимиты;
- `Restart=on-failure`, `SIGTERM` даёт время слить очередь записи (последние
  захваты не теряются при рестарте).

```bash
systemctl status ad-gateway
journalctl -u ad-gateway -n 50 -f
```

### 2.4 Режим «перехват портов» (сервисы сами открывают свои порты)

Так устроено на соревновании: сервисы самостоятельны и слушают свои порты, и
клиенты в конфигу не правятся — они как ходили на `хост:8083`, так и ходят.
Чтобы трафик шёл через мониторинг, вмешивается **уровень системы**: netfilter
поворачивает пакет, пришедший на публичный порт `P`, на слушатель гейта
`P + redirect_offset` (по умолчанию `+10000`). Отправитель не меняется —
классификация по IP остаётся честной. Апстрим тот же `127.0.0.1:P`: сервис
продолжает слушать свой порт, просто снаружи к нему никто не попадает напрямую.

В конфиге:

```json
"redirect_offset": 10000,
"ingress_ports": {
  "8083": "curs",
  "1337": "magiclib",
  "4444": { "service": "Omnyhub" },
  "3333": { "service": "Omnyhub" }
}
```

Гейт отдельно слушает `127.0.0.1:18083`, `127.0.0.1:11337`, `127.0.0.1:14444`,
`127.0.0.1:13333`. Маршрутизация тут **по порту слушателя**, а не по `Host`:
хоста у клиента нет — он дозванивается по `IP:порт`, и этот IP гейт не знает.
`Host`-маршруты (hostname-режим) остаются для DNS-клиентов и для проверок
оператора.

Правила применяет скрипт, читающий тот же конфиг (расхождение между
«что слушает гейт» и «что redirectит ядро» невозможно). Скрипт берёт не только
`ingress_ports`, но и `protected_ports` — их тоже разворачивает на гейт, чтобы
снаружи к базе/панели было не достучаться вовсе (`allow_protected_ports: true`
их пропускает), — и порты, добавленные в UI (`<data>/state/services.json`,
переменная `AD_STATE_DIR` при нестандартном расположении):

```bash
AD_GATEWAY_CONFIG=/opt/ad-gateway/config/gateway.json \
  bash deploy/iptables-forward.sh apply     # установить
bash deploy/iptables-forward.sh dump        # посмотреть
bash deploy/iptables-forward.sh flush       # убрать
```

Правила живут в цепочке `AD_FORWARD`, свежие копии вставляются в начало
`PREROUTING` (раньше docker/nat-правил). Для постоянства после перезагрузки
`flush` + `apply` можно повесить в `rc.local` или сервис; `install-linux.sh` умеет
применять их сразу, если `AD_APPLY_FORWARD=1`.

> Docker Desktop / Windows в этот режим не умеет (нет PREROUTING) — на стенде
> используется hostname-режим, на соревновании — перехват портов.

### 2.5 Что меняется на конец (checklist)

1. Перегенерить конфиг из шаблона с новыми адресами и паролями (`setup.js`
   уже входит в install).
2. `systemctl restart ad-gateway`.
3. Применить netfilter (`iptables-forward.sh apply`), если включён
   `ingress_ports`.
4. Прогнать пункты из `MONITORING.md`, «Предполётная проверка» — уже по боевым
   адресам. Минимально: `.git/config` от чекера проходит и не оборван,
   `.git/config` от подсети команды обрывает соединение, флаг чекера виден во
   вкладке «Чекер».
5. Если чекер или команды не входят в подсети из конфига — выставить их адреса
   во вкладке «Адреса» (UI), порты сервисов, не попавшие в `ingress_ports`, —
   во вкладке «Сервисы», и после этого ещё раз `iptables-forward.sh apply`.
   Неизвестный `Host` и порт базы должны давать обрыв соединения (код `000`).

### 2.6 Данные оператора

Всё то же, что и на стенде: `data/<сервис>/<дата>.jsonl`, `data/checker/…`,
UI на `:8787`, вкладки Обзор/Наша/Команды/Чекер/Флаги/Артефакты/Адреса/Сервисы.
Папка данных задаётся `AD_DATA_DIR` и принадлежит пользователю под сервисом.
Под ней же `state/`: `labels.json` и `services.json` — адреса и порты, заданные
в UI; переживают рестарт и применяются при старте автоматически.

## 3. Частые грабли

- **`EADDRINUSE` на слушателе портового режима.** Значит, `P + offset` уже занят
  другим процессом, либо offset перекрыл порт оператора — поднять `redirect_offset`.
- **`502 upstream unavailable: ECONNREFUSED 127.0.0.1:P`.** Сервис не слушает
  loopback: он внутри контейнера с пробросом. В этом случае в `ingress_ports`
  пропишите `upstream: "хост:порт"` или IP контейнера.
- **Трафик не идёт через гейт на соревновании.** Правила не применились или
  применялись при другом `redirect_offset`. `iptables-forward.sh dump` должен
  показывать те же цифры, что строка конфига.
- **Рестарт системы.** Гейт возвращается сам (`systemd`); сетевые правила —
  только если их добавили в автозагрузку (пункт 2.4).

## 4. Восстановление

- Процесс: `systemctl restart ad-gateway` — очередь записи сбрасывается, файлы
  не страдают.
- Откат конфига: перегенерить из шаблона, `restart`.
- Логи: `journalctl -u ad-gateway`, файлы захвата за дату в `AD_DATA_DIR`.
