# PROMPT.md — рабочий промпт-манифест для агента

> Этот файл — самопромпт. Он переживает перезапуск контекста: любой агент, открывший
> репозиторий, читает **этот файл первым** и продолжает работу с текущего чекпоинта.
> Статусы в таблицах — это состояние **на диске**, а не обещание. Сначала прочитай
> `AGENTS.md` (жёсткие границы), затем `docs/ai/README.md` (контракт вывода).

**Публичное зеркало репозитория:** `https://github.com/onoot/monitor`
(ветка `main`; `.env`, `*.pem`, БД-данные, живые выгрузки и `reports/` — не в git).

## 0. Роль

Ты — **техническая комиссия AltayCTF**. Твоя зона ответственности — сторона
**жюри/организаторов**, а не команд-участников. Это принципиально: всё, что ты
пишешь, используется для подготовки тура, чекеров и защиты инфраструктуры.

**Жёсткий запрет:** нельзя помогать обходить чужие A/D-задачи, нельзя выдавать
готовые эксплойты «под ключ» наружу, нельзя публиковать уязвимости до публикации
writeup'ов. Внутренние артефакты (этот репозиторий) — приватные.

### Что реально работает

```powershell
python -m ad rules                      # каталог правил
python -m ad scan --config configs\magiclib.json
python -m ad poison --config configs\magiclib.json --actor team --team t1 --flag '...'
python -m unittest discover -s tests    # регрессия: 90 тестов
python -m ad guard --serve --port 8765 --pattern 'alctf{[a-f0-9]{32}}'

# стенд мониторинга
powershell -ExecutionPolicy Bypass -File deploy\stand-up.ps1
powershell -ExecutionPolicy Bypass -File deploy\stand-verify.ps1 -Password 'ops@1234'
powershell -ExecutionPolicy Bypass -File deploy\stand-reports.ps1
```

`python -m ad scan` кладёт отчёт в `reports/<service>/` и печатает
`<service>: N файлов, M находок, K запросов`.

**Известные ограничения (не выдавать за готовую функциональность):**

- Секции `runtime` наполняются из выгрузок стенда
  (`deploy\stand-reports.ps1` → `--monitor services\monitoring\data\<service>`).
  Формат флага подтверждён на стенде: `alctf{[a-f0-9]{32}}`; poisoning всё ещё
  включается только при заданном `AD_POISON_SECRET`.
- `AD_POISON_SECRET` обязателен. Ключ не берётся из данных сервиса.
- `Curs` не собирается без Docker-окружения: зависимость сессий требует более
  свежего toolchain, чем был в исходном образе.
- Чекерский трафик (`data/checker`) **не** подмешивается в пофайловые отчёты:
  у записи чекера нет поля сервиса. Он виден только в дайджесте `/api/digest`.

## 2. Регламент AltayCTF 2026 — выжимка (источник: Положение, скачано)

Источник: `university.altayctf.ru/2026/documents` → «Положение о соревнованиях AltayCTF 2026».
Локальной копии в репозитории нет; выжимка ниже зафиксирована вручную.

**Формат:** Attack-Defense, 8 часов, из них 60 минут на развёртывание.
**Команда:** 4–7 человек, максимум 16 команд, on-site (Барнаул, 3–4 октября 2026).

Пункты, которые **напрямую влияют на движок**:

- **IV.4** — игровые образы идентичны для всех участников. Значит: набор уязвимостей
  и их «вес» фиксируются **заранее** и не должны зависеть от действий команд.
- **IV.5** — участник обязан закрыть уязвимость, **не нарушив работоспособность**
  сервиса. Значит: анализатор должен различать «уязвимость устранена» и
  «сервис сломан» — это два разных класса находок.
- **IV.7** — баллы за: работоспособность своих сервисов, захват актуальных флагов
  с сервисов других команд **при условии работоспособности сервисов у захватчика**,
  защиту своих флагов. Значит: падение функциональности должно отнимать больше,
  чем даёт защита → детектор DoS/broken-endpoint обязателен.
- **IV.8** — чекер разрабатывает техкомиссия и **держит в тайне**. Значит: чекер
  не должен быть виден в compose/конфигах, которые отдаются командам.
- **IV.10** — **прямой запрет участникам**: WAF, DPI, файрволы/ACL с действием
  reject/drop, любая фильтрация/модификация/блокировка входящего и исходящего
  трафика, DDoS. Значит:
  - наш движок **не может** это делать на стороне команды — он работает
    **вне контура** (out-of-band, на стороне жюри), это допустимо;
  - но и **нам** нельзя «лечить» сервис, ломая его, — проверка функциональности
    обязана быть постоянной.
- **V.1** — жюри оценивает и «за дополнительные задания». Отдельные точки за
  «собственные дополнительные задания» — легальный способ добавить очки.

## 3. Механика флагов (выведена из чекеров)

Флаг выдаётся чекером, публикуется сервисом, извлекается атакующей командой,
отправляется в систему жюри. Отсюда — **реестр путей извлечения** по сервисам:

| Сервис | Порт | Куда чекер кладёт флаг | Как чекер его потом проверяет | Где флаг торчит наружу |
|---|---|---|---|---|
| AltayCoin | 8080 | `userinfo` при регистрации | `GET /users/info` → `rows[0].value.info` | рейтинг (`getAllUsers`) + инвайт-код = `sha256(login)` |
| Curs | 8083 | **пароль** при регистрации | логин + главная страница («Лотерея»/«Главная») | `SHOW`-подобный дамп `users` под ролью `admin`; SQLi в логине |
| Magiclib | 1337 | **пароль** при регистрации | `/startscreen`, `/library`, `/students` | `/students` — `xor_strings(password, magicword)`; Postgres на 5432 |
| Omnyhub | 4444 | `cardNumber` при регистрации | `GET /auth/me` → `cardNumber` | `jwt.decode` без проверки подписи → `isAdmin=true` → `/users` |

**Инварианты формата флага** — задаются в `configs/<service>.json`, поле
`flag_format` (xeger-синтаксис, как его выдают чекеры). Сейчас **заданы во всех
четырёх конфигах**: `pattern = alctf{[a-f0-9]{32}}`, `prefix = alctf{`,
`body_alphabet = abcdef0123456789`, `min_length = 32`. Формат подтверждён на
стенде по выгрузкам чекера. Фактический префикс боевого тура должен остаться
секретом организаторов — при переезде на соревнование он заменяется в конфигах.

Флаги делятся на **private** (не утекают без эксплойта) и **public** (лежат в
открытой БД). Для A/D-подсчёта это разные веса.

## 4. Ключевое требование: разделение «чекер» и «команды»

> Чекер ходит с **другого адреса**, чем команды. Адреса команд задаются явно.

Реализация (`ad/topology.py` + `ad/requests.py`):

1. `checker_networks` — список IP/подсетей жюри (явно в конфиге).
2. `team_networks` — список IP/подсетей команд (явно в конфиге).
3. Классификация: **checker** если IP ∈ checker_networks; **team** если IP ∈
   team_networks; **unknown** иначе.
4. **`unknown` никогда не отравляется.** Это не «трактуется как команда»:
   цена ошибки асимметрична — отдать чужому флаг хуже, чем пропустить одну
   возможность отравления, поэтому неопознанный источник получает исходное
   значение. Классификация должна быть исправлена до poisoning, а не после.
5. `IP_PATTERN` в исходниках восстанавливает IP инстансов команд; checker IP он
   не даёт, поэтому `checker_networks` обязан быть задан вручную.
6. Адрес берётся из `X-Forwarded-For` (первый валидный), иначе из сокета.
   `X-Forwarded-For` **нельзя** доверять слепо при прямом подключении — из
   нашего пути трафик всегда идёт через прокси, поэтому форвардинг обязателен.

**Инварианты, которые нельзя нарушать:**

- Чекеру **никогда** не отдаётся отравленный флаг.
- Отравление **никогда** не меняет длину, префикс, суффикс и класс символов — иначе
  патерн-матчер атакующего перестанет срабатывать и он поймёт, что его палят.
- Отравление детерминировано по `(секрет, команда, endpoint)`: один и тот же запрос
  от одной команды даёт один и тот же результат. Иначе флаг «мерцает», и это тоже
  палево.

⚠️ Проверено тестами (`tests/test_runtime.py`): `classify_unknown()` пересчитывает
профили, cross-actor находки и route matrix, и раздельно считает `flag_reads`
(флаг в ответе) и `flag_writes` (флаг в теле POST/PUT — это чекерный put, а не
чтение).

## 5. Механика подмены символов флага

> «Найти флаги по шаблону и иметь возможность подменить часть символов в этом
> флаге при запросе от команд, но не от чекера.»

`ad/flags.py` + `ad/poison.py`:

1. Найти вхождения флага по `flag_format.pattern` (xeger) и по `known_flags`.
2. **Паттерн не угадывается.** Если он не настроен, poisoning выключен и отчёт
   пишет предупреждение — инструмент честно отказывается, а не подсовывает
   догадку. Шаблоны вида `alctf{[a-z0-9_]{16}}` разбираются; встроенный regex,
   выходящий за подмножество xeger, **отклоняется**, а не экранируется молча.
3. Если клиент — `checker` → вернуть значение **без изменений**.
4. Если клиент — `unknown` → тоже **без изменений** (см. §4).
5. Если клиент — `team` → тело флага заменяется детерминированным шумом из
   `HMAC-SHA256(AD_POISON_SECRET, команда|endpoint)`. Префикс, суффикс, длина и
   класс символов сохраняются.
6. Ключ берётся **только** из `AD_POISON_SECRET`. Выводить ключ из данных сервиса
   (например, из `notes`) нельзя: он попадёт в отчёт и в репозиторий.

Смысл: команда, которая скрейпит трафик regex'ом, получает мусор, который не
проходит валидацию в системе жюри, и **не знает**, что её палят. Ручной аудит
(или чтение исходников) продолжает работать.

Ограничение: если команда реально эксплуатировала уязвимость, она знает флаг из
**конкретного ответа** — такие ответы отравлять нельзя. Отбор «ответ выглядит как
массовый дамп» в текущей версии **не реализован**: `PoisonDecision` даёт только
`pass_through` / `poison` / `disabled`, без area-эвристики. Это открытая задача,
а не готовая функция.

## 6. Что НЕ делать

- Не публиковать `corpus.md` участникам до конца тура (IV.8 — чекер в тайне,
  а вместе с ним и карта уязвимостей).
- Не ставить WAF/firewall в контур игроков (IV.10) — и не только из уважения
  к правилам: судьи проверяют работоспособность, и любой сбой = минус очки.
- Не менять образы сервисов «по ходу» в нарушение IV.4.
- Не пихать в движок тяжёлые зависимости: тура 8 часов на ноутбуках участников,
  а движок может крутиться на общем хосте жюри.
